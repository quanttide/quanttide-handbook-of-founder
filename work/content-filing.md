# 内容归位

## 判断

内容发布之后到成为权威版本之间，有一段必须走完但不必当场走完的路。这段路的每一步都该省到极致——因为它是**发布之后**的负担，而发布时的灵感已经用完了。

归位的目的是让内容回到仓库，不是让内容在回位时被重新加工。

## 做法

1. **捕获**：沿用既有的收集习惯把原文放进 context 类仓库。不改一个字、不抽口径、不分类、不记账——原文里什么都有，再提炼一遍是重复劳动。
2. **回填**：自发布起 72 小时内完成入库。期限可调，但必须有期限；无期限的待办等于不存在。
3. **归位建议**：AI 给出 Top 3 候选目标仓库与路径，附理由；我确认或改判。我不作答，内容就留在工作集里，攒一批再处理。
4. **待办**：可省。文件已经躺在仓库里，遗忘的代价只是慢，不是丢；随手写下的「明天处理」是提醒，不是义务。

## 边界

- **不为归位新增流程**：归位要多走一步流程，说明这一步设计错了——它需要同时装载「仓库结构」和「文章主旨」两套上下文，而这一步根本不必当场完成。
- **不靠记忆与待办驱动**：靠待办驱动的归档会失败，靠目录驱动的不会。上岛和上岸是两件事，先上岛。
- **不代替发布时的判断**：归位只决定内容去哪，不改变内容本身；要改内容，回写作流程，不在这里改。
