# 智能体协作

## 总述

三条工作流都不直接产出内容，而是在安排「谁来做、谁来判、结果放哪、怎么回流」。它们共同构成一套**调度层工作流**，核心动作只有一个：把执行交出去，把判断留下。

## 分述

### 角色：按「谁做、谁判」分工

- Hermes 转发、Pi 执行、人验收。
- 手机判断、电脑执行、官网 App 解读。
- Zed 深度编辑、Pi 做项目交互、Hermes desktop 做跨仓整理。

划分的是职责边界，不是软件功能；工具只是角色的载体。

### 角色：执行与判断分离

手机端明确写「手机只做判断，不在手机上改代码」；派单模板固定有「验收人」；评审结论由人交回 Hermes。方向由人对齐，执行交给智能体，验收权不外包。

### 载体：仓库是唯一交换层

手机端不靠聊天记录收结果，靠 Working Copy 拉 GitHub 的分支、提交和产物；后台派单要求写清仓库、分支、产物路径，并回收四件交付物、跑测试。对话只是指令通道，仓库才是事实源。

### 载体：多入口、单职责

电脑端入口很多，但没有合并成一个入口，而是给每个入口写清职责，并把 OpenCode、dsh 明确标为补充。手机和电脑也共用同一套派单模板，只换入口。复杂度靠边界管理，不靠工具统一。

### 过程：异步闭环

三条工作流都假设「人会离开当前对话」：

```
派单 → 后台执行 → 查收 → 评审 → 回流成下一轮任务
```

后台派单的前提是「实现不留在当前对话」，移动端的前提是「人不在电脑前」。工作流围绕「人离开之后，工作还能继续」设计。

### 过程：契约化交接

派单四要素——对象、任务、交付、合格线——加上模板和派单前检查，让跨入口、跨设备的交接不依赖默契。协作从「靠人记」变成「照单执行」。

## 总结

三条工作流合起来，把人的位置收窄到四个动作：**澄清、派单、验收、回流**。其余环节交给智能体、设备和仓库。

但入口越多，协调成本越高。目前靠人记住「哪件事进哪个入口」和模板约束来维持，还缺一个统一的状态视图：谁在执行、卡在哪、下一轮是什么。Hermes → Pi 的两级转发链路也偏长，失败定位仍靠人；手机端的评审结论不回流，流程就断在评审这一步。
